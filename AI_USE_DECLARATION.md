# AI Use Declaration — StaySphere

## Tools used

Claude (Anthropic), used within Claude's chat interface with code
execution enabled, was used substantially throughout this project's
initial build.

## Where AI was used

- **Architecture and scoping:** Claude helped reconcile the original
  (very broad) feature wishlist with the INF2006 project brief's actual
  minimum requirements, and proposed the scoped-down feature set
  actually implemented (one guest workflow, one AI feature, one
  scalability mechanism) to fit the project timeline.
- **Backend code:** the FastAPI application (`src/backend/`) — models,
  schemas, auth, routers for auth/listings/bookings/ML/health — was
  generated by Claude and then run, tested and debugged interactively
  (e.g. a real bug in the booking "nights" calculation was found by
  running the code and fixed, not left unverified).
- **Frontend code:** the plain HTML/JS frontend (`src/frontend/`) was
  generated by Claude.
- **ML pipeline:** `analytics/train_price_model.py` was generated by
  Claude and executed to produce the actual metrics reported in
  `evidence/test-data-ai.md` — these numbers are real output from a
  real training run, not invented.
- **Synthetic dataset generator:** `data/generate_dummy_data.py` was
  written by Claude to produce placeholder data matching the publicly
  documented Airbnb dataset schema, since the real Kaggle dataset had
  not yet been downloaded at the time of this build.
- **Tests:** the automated pytest suites in `tests/` were generated by
  Claude and then actually executed; a test that initially failed
  (incorrect nights calculation) led to a real code fix, not a
  weakened test. 22 tests pass as of the latest run (2026-09-21),
  including new role-based-access tests added for the admin feature.
- **Frontend redesign and admin feature (second pass):** the frontend
  was restyled with a pill-shaped search bar and card grid layout
  inspired by common accommodation-marketplace UI conventions (not
  copied branding/assets — no Airbnb logo, colours or proprietary
  design elements were used), and an Admin Dashboard (listing
  create/edit/delete, platform analytics) with server-side role checks
  was added, along with seeded demo guest/admin accounts. This was
  actually run and tested (guest correctly gets 403 on admin routes,
  admin can create/update/delete a listing) rather than left unverified.
- **Documentation:** README, architecture doc, database schema doc,
  threat model, deployment guide, cloud trade-offs, responsible AI
  notes, and this declaration were drafted by Claude based on the
  actual implemented code and actual test/training output.

## Verification performed

- The full backend was actually run (not just written): the server was
  started, the database seeded, and the full guest workflow (register,
  login, search, view listing, book, cancel, my trips) was exercised
  end to end via curl and via the automated pytest suite.
- The ML model was actually trained; MAE/RMSE/R² figures in this
  submission are copied from real command output, not estimated.
- Security tests (SQL injection resistance, auth enforcement, password
  hashing, object-level authorization) were actually executed against
  the running application, not assumed.
- All 19 automated tests were run and passed as of 2026-09-21 — see
  `evidence/pytest-output.txt` for the raw output. After adding the
  admin/RBAC feature, the full suite (22 tests) was re-run and still
  passes.

- **Third pass (map, recommendations, admin operational visibility):**
  Claude added an interactive Leaflet/OpenStreetMap view of search
  results, replaced the standalone price-estimator as the primary
  guest-facing AI feature with a budget-based recommendation engine
  (`/api/recommendations`) that reuses the same trained regression
  model to flag "great value" listings, added a cosmetic
  simulated-payment UI step (verified client-side only — no payment
  field is ever sent to the backend or stored), and added admin-side
  visibility into all guest bookings plus a per-city price/demand
  overview and per-listing suggested-price gap. The end-to-end claim
  "a guest's booking shows up on the admin side" was specifically
  tested, not assumed — both by a new automated test
  (`test_booking_made_by_guest_is_visible_to_admin`) and by hand via
  curl (recommend → book → confirm visible in `/api/admin/bookings`).
  The Leaflet map itself could not be verified from within this build
  environment (it runs entirely in the end user's browser, and this
  sandboxed tool environment's network egress does not allow fetching
  from the CDN used to check it loads) — the team should open the app
  in a real browser to confirm the map renders before relying on this
  as evidence.

- **Fourth pass (real geo-heatmap, dataset coordinate fix, inspection
  script):** while building the admin geographic heatmap, Claude found
  and fixed a real bug in `data/generate_dummy_data.py` — listing
  latitude/longitude had been generated as fully random values across
  a wide box, uncorrelated with the listing's actual city, which would
  have made any real map view show overlapping nonsense rather than
  city clusters. Fixed to jitter coordinates around each city's real
  centre point instead, then regenerated the dataset, retrained the
  price model on the corrected data (metrics changed slightly as a
  result — see `evidence/test-data-ai.md` for the current numbers),
  and reseeded the database. Also found and fixed a second bug this
  surfaced: the price estimator's "key factors" list came back empty
  whenever the linear regression model (rather than the random forest)
  was selected, because only tree models expose `feature_importances_`;
  added a coefficient-magnitude fallback for linear models and a
  regression test for it. Also wrote `data/inspect_dataset.py`, a
  ready-to-run script for inspecting the real Kaggle dataset the
  moment it's downloaded (tested against the dummy dataset to confirm
  it works, output not fabricated).

## What still needs team verification

- The real Kaggle dataset has not yet been downloaded/inspected —
  once the team does this, they must re-run `analytics/train_price_model.py`
  and the data/AI tests against real data and update the evidence files
  and this declaration accordingly, since current metrics are on
  synthetic data.
- No AWS deployment has been performed yet — deployment steps in
  `docs/DEPLOYMENT.md` are written but unexecuted (marked "NOT YET
  EXECUTED" throughout) and need to be carried out and verified by a
  team member with AWS access.
- Team members should review, understand and be able to explain every
  part of the code they submit, not just the parts they personally
  wrote or verified above.
- Open the app in an actual browser and confirm the search-results map
  renders (tiles load, markers appear, clicking a marker opens the
  listing) — this could not be verified from the sandboxed build
  environment used to write this code.
